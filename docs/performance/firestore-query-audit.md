# Auditoria Firestore: consultas, índices e desempenho

## 1. Escopo e nível de evidência

Auditoria read-only em 2026-10-09: código de frontend Web SDK, backend Admin/callables, MCP, OAuth e helpers; configuração de índices de produção listada via CLI autenticada existente. Nenhuma consulta a registros de produção, benchmark, Query Explain, build, deploy, alteração de índice, código, regra ou dado foi realizada. **Há desperdícios comprovados por leitura de código; não há medição que atribua a lentidão percebida exclusivamente ao Firestore.** Cold starts, rede, tamanho de resposta e CPU precisam de telemetria separada.

Código main contém pause futuro; produção informada pelo Lead é release 4d42a63 sem pause. As propostas abaixo NÃO são índices já criados nem garantia de velocidade.

## 2. Resposta direta: “100 examinados, 0 abertos”

[PendingPage:74–113](../../apps/frontend/src/PendingPage.tsx#L74-L113) usa **Web SDK direto**, não consulta backend de pendências: coleção própria, orderBy(documentId()), cursor startAfter e limit(100), **sem where**. Depois aplica rows.filter(isOpen) em memória. Assim, 0 significa nenhum aberto **nesses 100 documentos**, não no histórico inteiro. A ordem por ID não é cronológica. Próxima página continua pela última identidade carregada, não pelo último aberto.

O [sino:39–44](../../apps/frontend/src/PendingPage.tsx#L39-L44) usa outro useRows: listener na coleção própria limit(100), sem filtro. Conta em memória os abertos há mais de 8h. [useRows:41–72](../../apps/frontend/src/data.ts#L41-L72) não possui where, ordenação temporal, cursor, cache compartilhado ou total global. Dashboard tem uma terceira assinatura de registros próprios [linha 188](../../apps/frontend/src/Dashboard.tsx#L188). Ao coexistirem sino, dashboard ou página de pendências, há intenções de leitura duplicadas; o SDK pode reaproveitar cache/targets idênticos, mas não se deve declarar cobrança multiplicada exata sem medição. A consulta de Pending com orderBy explícito é diferente do listener genérico.

**Índice sozinho não corrige isso:** a query não pede “abertos”. [isOpen:1–7](../../apps/frontend/src/pending-utils.ts#L1-L7) usa falsy endedAt; backend listOpen só aceita undefined [record-editing:126–146](../../apps/backend/src/modules/registration/infrastructure/firestore-record-editing.ts#L126-L146); pause aceita undefined/null. Há divergência semântica. Igualdade endedAt == null não inclui campo ausente; != também não é teste de ausência. Não substituir o scan por null sem tratar legado.

### Solução segura proposta

Definir estado derivado explícito, por exemplo recordState='open'|'closed', mantendo startedAt/endedAt como fatos. Todas as escritas Admin devem atualizar estado atomicamente: register, closePrevious, update_record incluindo reabertura, pause origem/sucessor, imports autorizados e qualquer caminho futuro. Merge deve preservar estado. Não inventar endedAt para completar esquema.

Após cobertura verificável e timestamp canônico derivado disponível (ver seção 7): coleção própria where(recordState=='open').orderBy(startInstant asc).limit(100), cursor composto; sino pode consultar abertos com startInstant abaixo do cutoff de 8h ou agregado autorizado. Índice proposto COLLECTION records(recordState ASC, startInstant ASC); documentId desempata. A passagem do tempo exige reconsultar cutoff ou contar localmente em um conjunto **completo de abertos**, não sobre a primeira página de fatos.

Sem backfill autorizado, manter categoria “legado ainda não classificado” e aviso de cobertura; opcional fallback paginado explícito, nunca declarar zero global. Não executar backfill automático/histórico neste trabalho. Antes de migrar, reconciliar null, ausente, string vazia e datas inválidas sem apagar evidências. Leitura Web continua apenas owner; não abrir collectionGroup público para resolver pendências.

## 5. Custo e gargalos reais: além dos índices

1. **Relatório pessoal lê histórico inteiro mesmo para um dia/projeto.** Para N fatos owner, são aproximadamente N leituras de records (mais queries vazias finais em múltiplos exatos501), mais metadata por página+catalog final+archive+topics. Se só20 fatos da semana interessarem, N ainda é lido. Acima2000 visíveis falha conservadoramente, não total parcial.
2. **Company/project releem fatos**: seleção completa + contexto de cada pessoa. Project ainda lê primeira página preliminar e a repete. Company páginas100 amplificam round trips; context UID sequencial aumenta caminho crítico. Limit informado pela UI não é knob efetivo para total completo atual.
3. **Limites não são limites de cobrança raw**: global-context e completeSelection contam visíveis. Muitos pessoais filtrados da seleção company, referências desconhecidas ou ACL negadas podem gerar scan grande antes de atingir2000. scannedCount visible mascara trabalho real. Registrar rawScanned, visibleCount, query/pageCount, metadataReadCount separadamente, sem IDs/títulos privados.
4. **Consistência metadata**: global-context lê records em tx, porém catalog por db.getAll fora dela. Projetos podem mudar tipo/ACL entre páginas/catalog final. Cache ingênuo torna isso pior. Daily já usa tx.getAll e Map dentro tx: padrão mais apropriado para request, com limites e negative cache.
5. **CPU também pesa**: [global-estimates:62–100](../../apps/backend/src/modules/reports/domain/global-estimates.ts#L62-L100) busca próximo início com find e soma fatos com filter/reduce para cada aberto; aproxima O(abertos*N), potencial quadrático. Pré-agrupar por UID/projeto e pré-calcular fatos por dia reduz CPU sem alterar política, mas requer testes equivalentes de sobreposição/fuso/DST.
6. **Projeto catálogo** relido inteiro por múltiplos hooks (página, drawer, editor) e MCP search antes de filtrar. Callable cursor só pagina array depois do scan; não evita leituras anteriores. N+1 metadata não significa100 RPCs por100 projetos: getAll batch reduz RPC, mas cada doc continua leitura.
7. **Refetch**: [PersonalPage:145–199](../../apps/frontend/src/PersonalPage.tsx#L145-L199) refaz relatório em from/to/zone/attempt/includeArchived/company/projectId. Flag active ignora resposta antiga, não cancela operação cobrada no servidor. Nova seleção de projeto preserva contexto global e portanto não economiza records hoje. Não há polling nesse efeito; useClock do sino só calcula localmente, não deve ser acusado de requery periódico sem evidência.

Documentos devolvidos não são toda a fatura: queries vazias têm cobrança mínima; listeners cobram inicial/mudanças/reconexões conforme persistência; index entries e agregações têm regras próprias. Não publicar reais/latência a partir de contagem estática. [Preços oficiais](https://firebase.google.com/docs/firestore/pricing).

## 7. Otimizar relatórios sem quebrar personal-v3/ACL

Política global limita estimativas pelo mínimo de agora,4h,meia-noite do fuso,próximo início válido mesmo UID/projeto e orçamento diário8h menos fatos fechados. Fatos explícitos não são truncados; seleção de projeto, arquivo ou tópico não pode devolver orçamento “livre” ignorando fatos de outros projetos autorizados. Company nunca deve usar fatos pessoais de colegas para estimativas ou expor contagem/título. Projetos desconhecidos/metadata inválida falham fechados. Restringir apenas startedAt>=from e projectId antes do contexto muda resultados silenciosamente.

**Antes de qualquer índice temporal:** [work-model](../../apps/backend/src/modules/registration/domain/work-model.ts) aceita ISO com offset e [register:215–243](../../apps/backend/src/modules/registration/infrastructure/firestore-work.ts#L215-L243) preserva input sem normalizar startedAt/endedAt. Ordem lexicográfica das strings com offsets distintos não é ordem de instantes. Portanto where/orderBy temporal direto nos campos strings atuais NÃO é uma solução correta. Usar Timestamp canônico derivado (por exemplo startInstant/endInstant) ou projeção/sidecar versionado, preservando fala e strings originais. Cobertura histórica exige plano autorizado; não supor todos documentos já preenchidos nem fazer backfill automático. Índices temporais propostos na tabela são formas lógicas condicionais e devem usar os campos canônicos finais, não as strings atuais. Fatos fechados sobrepostos requerem startInstant < dayEnd E endInstant > dayStart (ou decomposição/união completa equivalente), inclusive cruzamento da meia-noite; abertos têm ramo separado. Contexto do orçamento deve conter todos os projetos autorizados nos mesmos dias civis afetados, não apenas o projeto selecionado.

Desenho de evolução: uma camada read model por UID/dia com intervalos fechados cruzando dias, referências de abertos e sucessores relevantes; cálculo global primeiro, filtros de visualização depois. Manter versões de política, evidência factual, timezone/DST, asOf para estimativas e invalidar em update/reopen/pause/merge/archive/ACL. Alternativa inicial: reduzir histórico com conjunto de candidatos intervalares completo comprovado e contexto do dia, sem materialização; precisa considerar fato iniciado antes de from que termina dentro/depois da janela, aberto antes da janela, fuso misto e o próximo início após janela. Contagem agregada simples não substitui contexto de intervalos. Nunca apagar histórico para ficar abaixo2000.

Personal project report atual já autoriza projeto antes, mas usa CG e filtra owner depois: oportunidade de owner collection antes de leitura como merge corrigido, preservando canonical uid e cursor compatível. Não confundir ausência de vazamento na resposta com ausência de leituras desnecessárias Admin. Helper legado também merece guard canônico se futuramente conectado.

## 8. Plano priorizado e validação

**P0 — Correção de cobertura/observabilidade, baixo risco:** manter aviso0=no lote; harmonizar definição de aberto; expor páginas/cobertura honesta. Instrumentar durations (auth/query/context/catalog/cpu/serialize), raw/visible/query counts e tamanho resposta sem conteúdo privado. Medir p50/p95 warm/cold, datasets crescentes e clock fixo. Não executar queries de produção extras sem autorização.

**P1 — Economias sem alterar fatos:** request-local metadata Map com negative cache e tx-compatible ACL; reutilizar catalog entre archived/topics; retirar readPage preliminar redundante preservando erro/archive/ACL; deduplicar project hooks e report in-flight no mesmo UID/seleção. Revalidar ACL por request e em mudanças. Melhorar CPU com equivalência de testes. Paginação raw budget separado pode impedir scans excessivos, mas deve retornar erro/partial explícito, não total completo falso.

**P1 — Pendências indexadas:** definir estado derivado e atualizar todos caminhos em tx; plano de compatibilidade/backfill separado, confirmado e auditado; então query/índice open. Testar >100 fechados antes de1aberto, null/ausente/inválido, reabertura, pause, UID trocado, paginação e botão carregar mais. Não prometer full count antes disso.

**P2 — Reports window-aware/read model:** validar conservação de fatos e orçamento8h global com testes regressivos antes de reduzir scans; solicitar Query Explain e métricas autorizadas depois. Propor índices mínimos para queries finais, não para scans atuais que não têm where temporal.

**P2 — Catálogo/ACL:** separar queries work e personal owner com legado explícito; paginação Firestore real e limites seguros. Texto search pode pedir catálogo cacheado seguro ou serviço específico se volume justificar, não uma lista infinita de compostos.

**Cache:** keys incluem UID, escopo, fuso, período, seleção, includeArchived, policy/version e clock/asOf. Sem cache global de resposta pessoal. TTL sozinho não basta para revogação/metadata; invalidar após mutations e logout/UID, e nunca reutilizar decisão ACL entre usuários. ## 9. Adendo: alerta na página Projetos e cache em memória

O screenshot motivou revisão específica: [useProjects:25–45](../../apps/frontend/src/useProjects.ts#L25-L45) chama [loadAllProjects:6–20](../../apps/frontend/src/project-list.ts#L6-L20), que continua **todas as páginas** até nextCursor ausente e rejeita cursor repetido. Assim 100 é tamanho de cada resposta, não limite total de projetos na UI. Entretanto o backend listProjects chama listProjects repository em cada página, e este relê projects.limit1001 antes de filtrar ACL/cursor em memória. Para P projetos totais<=1000 e V autorizados, o carregamento completo tem aproximadamente ceil(V/100) scans de P documentos (mínimo1 request), mais os scans de outras instâncias de hook. Mais1000 globais gera erro conservador, não lista parcial silenciosa.

[Dashboard:524–527](../../apps/frontend/src/Dashboard.tsx#L524-L527) mostra alerta quando **projects.rows.length===100 OU records.rows.length===100**, independentemente de mode. Portanto Projetos pode avisar por causa dos100 records carregados ocultamente; se houver exatamente100 projetos completos, também avisa incorretamente. Não é condição >=100 no código observado. [DataTable:110–111](../../apps/frontend/src/Dashboard.tsx#L110-L111) ainda diz até100 e [linha144](../../apps/frontend/src/Dashboard.tsx#L144) repete warning por tamanho, não metadado de cobertura. Separar cobertura por dataset e tela; não inferir truncamento de igualdade ao batch size.

Cache/repository frontend compartilhado por UID+scope+includeArchived+backend instance, com dedup in-flight, reduzirá latência de remount e scans duplicados. Não elimina o scan inicial backend por página, não resolve >1000 catálogo global, e não é índice. Invalidar em create/update/archive/merge/topic mutations, logout/UID e refresh explícito; não compartilhar ACL decisions entre usuários.
